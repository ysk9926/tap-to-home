# ADR 0007 — Realtime 단일 소유자와 조회 보정

날짜: 2026-09-20 · 상태: 채택

## 문제

레이스와 친구 감시가 같은 `u:{userId}` 채널을 각자 구독·해제하지만 supabase-js 2.116.0은 같은 topic에 같은 객체를 반환한다. 두 번째 구독은 연결 상태를 받지 못하고 페이지 cleanup이 공유 채널을 제거한다. 연결되지 않으면 2초·5초·20초 폴링이 사용자당 분당 45회 GET을 만든다.

## 결정

- 인증된 앱 layout의 `LiveSyncProvider`가 채널·친구 조회·신호 수신을 소유한다. 내 채널의 모든 리스너를 먼저 등록하고 한 번 subscribe한다.
- React와 독립된 세션 컨트롤러가 생성·해제를 직렬화하고 친구 ID 차이만 반영한다. 늦은 이전 세대 콜백은 무시한다.
- 내 채널과 친구 채널의 건강 상태를 구분한다. 레이스는 필요한 전체 채널이 연결된 경우에만 정상이다.
- 정상 연결은 60초 보정 조회, 장애는 기존 2초·5초·20초 폴링이다. 숨김·오프라인은 신규 GET을 중지하고 재연결·복귀·자정에는 중복을 합쳐 보정한다.
- 정기 조회 타이머는 캐시 갱신과 분리한다. TanStack Query의 `refetchInterval`은 `setQueryData` 때 다시 시작되므로, 지속적인 탭·실시간 이벤트가 보정 조회를 미루지 않게 한다.
- 복귀 보정의 중복 판단에는 실제 조회 성공만 사용한다. 실시간 캐시 갱신 시각으로 전체 스냅샷 조회를 생략하지 않는다.
- TanStack Query 키에 사용자 ID를 포함한다. 친구·신호는 Provider가 한 번 조회하며 페이지는 같은 상태를 소비한다.
- 신호는 클라이언트의 실제 수신 확인으로 읽음 처리한다. Realtime 서버 접수만으로 푸시를 제외하지 않는다. 기존 `Signal.readAt`을 사용하며 DB 스키마는 유지한다.
- Vitest의 기존 node 테스트를 유지하고, Provider 생명주기·가시성 테스트에 React Testing Library와 jsdom을 개발 의존성으로 사용한다.

## 대안과 결과

폴링 간격만 늘리면 1초 이동 목표와 채널 충돌이 해결되지 않는다. 별도 WebSocket 서버·통합 API는 운영 범위를 늘리므로 도입하지 않는다. 정상 상태에서 분당 GET 약 3회를 목표로 하며, 실제 환경의 Realtime 키와 연결이 갖춰져야 한다. 이벤트 유실은 60초 보정으로 수렴한다. 인앱 수신 확인과 FCM 발송 사이의 경합에 따른 중복까지 정확히 한 번으로 보장하지 않는다.

설계·검증 기준은 [조회 효율 설계](../superpowers/specs/2026-09-20-query-efficiency-design.md), 실행 순서는 [구현 계획](../superpowers/plans/2026-09-20-query-efficiency.md)에 있다.
